## Verdicts

- **Export works.** ONNX opset {opset}, dynamic batch and time axes, output `logits`
  (log-softmax and CTC decode are numpy). The fp32 ONNX model reproduces torch on 0.8 s,
  3 s and 8 s clips (table below) and reproduces every P02 GOP number to three decimals.
- **int8 {gate_verdict} the P02 verdict.** Gate G0 is {torch_pass} for torch and
  {int8_pass} for int8. The largest per-phoneme GOP change is {max_delta} nats; segment
  boundaries and competitors are identical. This is one word pair from one speaker: the
  same evidence P02 rested on, not new evidence about int8 in general. Under the rule of
  P04, int8 is therefore **not rejected**.
- **Condition on using int8.** On single frames the log-posteriors move by up to 2.8 nats
  (mean 0.3-0.4), even though the aligned phonemes' GOP moved by at most {max_delta}.
  G1 (P25) must run on the exact model that will be deployed and its thresholds must be
  calibrated on it. Do not calibrate on fp32 and deploy int8, or the reverse.

## Method

- `export.py`: legacy TorchScript exporter (`dynamo=False`; it worked on the first try, so
  the default dynamo exporter was not tried), eager attention, traced on 3 s of noise,
  weights inline (1.26 GB file). The tracer warns that a mask tensor becomes a constant;
  parity on 0.8 s and 8 s clips shows the time axis is really dynamic.
- `quantize.py`: onnxruntime dynamic quantisation, int8 weights, **MatMul only**. With all
  op types the tool fails on the weight-normalised positional convolution ("Expected ...
  to be an initializer"), so the convolutions stay fp32. `quant_pre_process` was skipped
  (its symbolic shape inference fails on this graph). Peak memory of the tool was 4.0 GB;
  run it under a memory cap (two uncapped runs coincided with the 8 GB WSL VM restarting,
  most likely from memory exhaustion).
- `parity.py`: torch vs onnxruntime on four clips, log-softmax in float64.
  `gop_check.py`: the P02 pipeline (same clips, alignment, GOP formula, gate) fed by
  ONNX log-posteriors.
- `bench.py`: one process per (model, clip, threads); 5 warm-up runs, then 50 timed runs
  of normalise + `session.run` + log-softmax on one real read-speech clip (first 3 s and
  first 8 s of one LibriSpeech dev-clean utterance). Alignment, GOP and audio decoding
  are not timed. Times are p50 / p95 in ms, with the real-time factor at p50 in brackets.
- `concurrency.py`: pinned to N physical cores, one shared session with one intra-op
  thread, k Python threads released together, latency from release to completion
  (queueing included), 6 bursts per k, p95 over all requests, k raised until p95 exceeds
  2000 ms twice in a row.

## Limits: read before quoting a number

- **This is not the target VPS.** The project docs give only a budget (`$0-7` per month,
  PLAN-v7 section 11), not a machine. This run used an 11th-gen laptop CPU under WSL2.
  Per core it is likely faster than a small VPS; by how much was not measured, and no
  scaling factor is assumed here. The scripts are self-contained: run the commands below
  on the real VPS and replace the tables.
- With more cores the measured burst capacity falls short of the arithmetic estimate
  (`floor(2000 / single-request time) x cores`; 3 vs 4 for fp32 and 7 vs 12 for int8 on
  4 cores), so cores are not fully independent (shared cache and memory bandwidth, and
  the guest's idea of "physical" cores may not match the host). Use the measured value.
- A burst of simultaneous requests is a demanding pattern. Sustained throughput is about
  `cores / single-request time`.
- Excluded from the timings: g2p, alignment, GOP arithmetic (numpy, small next to
  the model), audio decoding and upload, HTTP. Budget for them separately.
- Memory decides more than speed on a small VPS: fp32 needs 2.1-2.3 GB resident and int8
  0.8-1.1 GB, so neither fits a 1 GB machine comfortably.
- Four clips and one word pair: enough to reject a broken export, not to certify int8.

## Reproduce

```bash
export DATA_DIR=~/sonari-data                       # audio, models and results live here
uv run --directory spikes/gop python onnx/export.py
# The quantiser holds several copies of the 1.26 GB model. Cap its memory:
systemd-run --user --scope -p MemoryMax=5500M -p MemorySwapMax=0 \
  uv run --directory spikes/gop python onnx/quantize.py --ops MatMul
for m in fp32 int8; do
  uv run --directory spikes/gop python onnx/parity.py --model $m
  uv run --directory spikes/gop python onnx/gop_check.py --model $m
  for c in speech_3s speech_8s; do for t in 1 2 4; do
    uv run --directory spikes/gop python onnx/bench.py --model $m --threads $t --clip $c
  done; done
  for c in 1 2 4; do uv run --directory spikes/gop python onnx/concurrency.py --model $m --cores $c; done
done
uv run --directory spikes/gop python onnx/report.py
```

Models and results are not committed (`DATA_DIR`); only the scripts and this report are.
